
# 開発フロー

## 1. 目的

本書は、`juchu01` を基準とするバージョンアップ開発（`ver.2`～`ver.5`）において、各バージョンの成果物作成、実装、テスト、報告を一貫した手順で進めるための標準フローを定める。

各工程の成果物を次工程の入力として扱い、仕様・設計・テスト・実装・結果報告の整合性を確保する。

## 2. 基本方針

- 仕様書・設計書・テスト仕様書は、原則として実装前に作成する。
- テスト仕様書は設計内容を基に作成し、実装着手前にテスト項目と期待結果を確定する。
- 実装は、仕様書・設計書・テスト仕様書に定めた内容を満たすように行う。
- テストは、事前に作成したテスト仕様書に従って実施する。
- 改修詳細報告書は、実装とテストが完了した後、実際の改修内容とテスト結果に基づいて作成する。
- 不具合や仕様変更が発生した場合は、関連する仕様書・設計書・テスト仕様書・報告書への影響を確認し、必要な資料を更新する。
- 各バージョンの成果物は、対象バージョンのフォルダーに整理して保存する。

## 3. 標準開発フロー

### 3.1 仕様書作成

改修要件を確認し、目的、対象範囲、機能要件、制約条件を整理する。

改修対象と対象外を明確にし、実装する機能の範囲を定義する。

**成果物：** 仕様書

### 3.2 設計書作成

仕様書を基に、処理方式、画面、クラス、DAO、データベースなどの変更内容を設計する。

必要に応じて、処理フロー図、シーケンス図、クラス図、ER図などを作成する。図の種類と名称は、実際に表現している内容に一致させる。

**成果物：** 設計書、必要な設計図

### 3.3 テスト仕様書作成

仕様書・設計書を基に、テスト観点、前提条件、入力データ、操作手順、期待結果を定義する。

実装前にテスト項目と合格条件を確定する。テスト仕様書には、原則として実施後の結果や合否を記載しない。

**成果物：** テスト仕様書

### 3.4 実装

仕様書・設計書・テスト仕様書に従って、ソースコード、データベース定義、設定ファイルなどを変更する。

実装中に仕様や設計との不一致が判明した場合は、関連資料への影響を確認し、必要に応じて資料を更新してから実装を進める。

実装は、事前に定義したテスト仕様書の期待結果を満たすことを目標とする。

**成果物：** 変更したソースコード、SQL、設定ファイルなど

### 3.5 実装確認

コンパイル、起動、基本操作などを確認し、明らかな実装上の問題を解消する。

テスト仕様書の期待結果と実装内容に矛盾がないことを確認する。

**成果物：** 実装確認の記録（必要に応じて）

### 3.6 テスト実施

テスト仕様書に記載した前提条件、入力データ、操作手順に従ってテストを実施する。

各項目について実際の結果を記録し、期待結果と比較して合否を判定する。

不合格が発生した場合は、原因を調査し、必要な修正を行ったうえで、修正箇所と影響範囲を再確認する。

通常の画面操作では実施できない条件や、仕様の対象外となる操作は、通常の機能テスト項目に混在させない。必要な場合は、目的と対象を明確にして別途扱う。

**成果物：** テスト結果の記録、テスト結果報告書

### 3.7 改修詳細報告書作成

実装とテストが完了した後、実際に変更した機能、変更理由、主な実装内容、データベース変更、テスト結果を整理する。

報告書は、提出先が単体で改修内容を理解できるように作成する。提出対象外の内部資料やファイルを参照しなければ理解できない構成にしない。

**成果物：** 改修詳細報告書

### 3.8 最終整合性確認

仕様書、設計書、テスト仕様書、ソースコード、テスト結果報告書、改修詳細報告書の内容を照合する。

機能名、クラス名、テーブル名、テスト件数、合否などに不一致がないことを確認する。

成果物に更新漏れや矛盾がないことを確認してから、そのバージョンを完了とする。

## 4. 各工程の完了条件

| 工程 | 完了条件 |
|---|---|
| 仕様書作成 | 改修目的、対象範囲、機能要件、制約条件が明確である |
| 設計書作成 | 仕様を実現する処理方式と変更対象が説明されている |
| テスト仕様書作成 | テスト手順、入力、期待結果、合格条件が実装前に定義されている |
| 実装 | 仕様書・設計書に沿って変更され、明らかな実装上の問題が解消されている |
| 実装確認 | コンパイル、起動、基本操作などの確認が完了している |
| テスト実施 | テスト仕様書の各項目について実際の結果と合否が記録されている |
| 改修詳細報告書作成 | 実際の改修内容とテスト結果が報告書単体で理解できる |
| 最終整合性確認 | 成果物間に重大な記載漏れや矛盾がない |

## 5. バージョンごとの成果物構成例

```text
ver.N/
├─ 仕様書/
│  └─ ver.N_仕様書.docx
├─ 設計書/
│  ├─ ver.N_設計書.docx
│  └─ UML/
├─ テスト/
│  ├─ ver.N_テスト仕様書.docx
│  └─ ver.N_テスト結果報告書.docx
└─ 報告書/
   └─ ver.N_改修詳細報告書.docx
```

実際のリポジトリ構成に合わせてフォルダー名を調整してよい。ただし、各成果物の保存先と対象バージョンが明確に分かる構成とする。

## 6. GitHubでの管理

- 仕様書・設計書・テスト仕様書は、実装前の内容が分かるように、各工程の区切りでコミットする。
- 実装変更は、対象バージョンのソースコードと対応付けて管理する。
- テスト仕様書とテスト結果報告書を区別し、事前計画と実施結果を混在させない。
- 改修詳細報告書は、テスト完了後の確定内容を反映してコミットする。
- コミットメッセージには、対象バージョンと変更内容が分かる説明を付ける。
- GitHubの履歴を利用して、仕様変更、設計変更、実装変更の経緯を追跡できるようにする。

## 7. バージョン完了チェックリスト

- [ ] 仕様書が改修要件と一致している
- [ ] 設計書が仕様書と一致している
- [ ] テスト仕様書が仕様書・設計書と一致している
- [ ] テスト仕様書が実装前に作成されている
- [ ] 実装が仕様書・設計書・テスト仕様書を満たしている
- [ ] 実装確認が完了している
- [ ] テスト結果が記録され、各項目の合否が明確である
- [ ] 不具合修正後、必要な範囲の再テストが実施されている
- [ ] 改修詳細報告書が実際の改修内容とテスト結果を反映している
- [ ] 図の種類・名称（例：シーケンス図、処理フロー図）が内容と一致している
- [ ] 成果物間で名称、件数、結果などの記載に矛盾がない
- [ ] 対象バージョンの成果物がGitHubに保存されている
