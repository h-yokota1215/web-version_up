# juchu01 バージョンアップ別DB改修方針

## 1. 対象DBの現状

DB接続先は、`DaoConnectionManager.java`で次のように定義されている。

```text
jdbc:h2:tcp://localhost/~/coscommon01
```

現在のDBは、次のSQLで構築される。

- `sql/create.sql`：テーブル定義

- `sql/insert.sql`：初期データ

- `sql/select.sql`：確認用SQL

主な既存テーブルは以下の通り。

| 分類 | テーブル |
|---|---|
| 法人顧客 | `KOKYAKUHOUJIN_TABLE` |
| 顧客認証 | `KOKYAKUPASS_TABLE` |
| 商品 | `BUNGU_TABLE`、`BOOK_TABLE` |
| 商品カテゴリ | `GSUBCTG_TABLE`、`CTR_GCTG_TABLE` |
| 在庫 | `HANBAIZAIKO01_TABLE`～`HANBAIZAIKO03_TABLE` |
| 受注 | `JUCHU_TABLE`、`JUCHUMEISAI_TABLE` |
| 採番 | `CTR_CURCODE_TABLE` |
| エラー・出荷関連 | `ERR_*`、`WK_*`テーブル |

## 2. DB共通方針

### 2.1 既存データの扱い

- 既存の法人顧客、文具、書籍、受注データは削除しない。

- 改修前後で既存データを利用できることを回帰テストで確認する。

- `create.sql`と`insert.sql`は原本として保持し、改修用SQLは別ファイルで管理する。

- 改修用SQLは、実行順序と再実行可否を明記する。

### 2.2 命名・型の方針

- 既存の大文字スネークケースを基本的に踏襲する。

- 既存のコード体系と桁数を変更する場合は、プログラム側の全利用箇所を同時に確認する。

- 金額は既存の`INT`型を基本とし、円単位の整数で保持する。

- 日付・日時は既存の`DATETIME`型を踏襲する。

- 新設テーブルには主キーを定義する。

- 現行DBには外部キー制約がないため、改修時に追加する場合は既存処理への影響を確認する。

### 2.3 テストデータの方針

- バージョンごとに追加・変更したデータを`insert`用SQLまたはテスト用SQLで管理する。

- 正常系、境界値、エラー系のデータを準備する。

- テスト後に在庫、採番、売掛残高などの更新結果を確認する。

## 3. ver.2 商品カテゴリ拡張

### 3.1 DB改修対象

| 対象 | 現状 | 改修内容 |
|---|---|---|
| `CTR_GCTG_TABLE` | 文具・書籍の2カテゴリ | 食品・AV機器・PCのカテゴリを追加 |
| `GSUBCTG_TABLE` | 文具・書籍のサブカテゴリ | 新カテゴリのサブカテゴリを追加 |
| 商品テーブル | `BUNGU_TABLE`、`BOOK_TABLE`のみ | 食品・AV機器・PC用テーブルを追加 |
| 在庫テーブル | 既存商品分の在庫 | 新商品分の営業所別在庫を追加 |
| `MAKER_TABLE` | 既存メーカー情報 | 新商品で必要なメーカーを追加 |
| 画像関連 | 既存画像パスを保持 | サンプル画像のパスを登録 |

### 3.2 推奨テーブル方針

商品カテゴリごとに固有項目が異なり、現行も`BUNGU_TABLE`と`BOOK_TABLE`を分けているため、ver.2では次のテーブルを新設する方針とする。

- `FOODS_TABLE`：食品固有項目を保持する。

- `AV_TABLE`：AV機器固有項目を保持する。

- `PC_TABLE`：PC固有項目を保持する。

各テーブルには、既存商品テーブルと同様に次の共通項目を持たせる。

- 商品コード

- 商品名

- 入数

- 単位

- 標準単価

- メーカーコード

- コメント

- 画像URI

- 商品種別

カテゴリ固有項目は、サンプルデータの項目に合わせて各テーブルに追加する。

### 3.3 カテゴリコード方針

既存コードは以下の通りである。

| コード | クラス名 | カテゴリ |
|---|---|---|
| `01` | `Bungu` | 文具 |
| `02` | `Book` | 書籍 |

新カテゴリは、商品コードの先頭番号およびサンプルデータと整合するコードを割り当てる。
例として、食品・AV機器・PCを`03`・`04`・`05`とする場合、`CTR_GCTG_TABLE.CLASSNAME`には対応するJavaクラス名を登録する。

### 3.4 移行・初期データ

- `CTR_GCTG_TABLE`へ新カテゴリを追加する。

- `GSUBCTG_TABLE`へサブカテゴリを追加する。

- ver.2サンプルExcelの食品・AV機器・PCデータを商品テーブルへ登録する。

- `HANBAIZAIKO01～03_TABLE`へ各商品の営業所別在庫を登録する。

- 画像URIは`WebContent/img`配下の実際の配置先と一致させる。

- 商品コードが一意であることを確認する。

### 3.5 DBテスト

- 新カテゴリがカテゴリ一覧に表示されること。

- 各カテゴリの商品一覧が取得できること。

- 共通項目と固有項目が正しく取得できること。

- 営業所ごとの在庫・引当数が取得できること。

- 既存の文具・書籍データが引き続き取得できること。

## 4. ver.3 個人顧客対応

### 4.1 DB改修対象

| 対象 | 現状 | 改修内容 |
|---|---|---|
| 顧客情報 | `KOKYAKUHOUJIN_TABLE`のみ | 個人顧客を保持する構造を追加 |
| 顧客認証 | `KOKYAKUPASS_TABLE` | 個人顧客も認証可能にする |
| 顧客コード | `CHAR(6)`、法人コードは`100000`台 | 個人コード先頭を4～8にする |
| 受注 | `KOKYAKUCD`を保持 | 個人顧客の受注を登録可能にする |
| 支払方法 | `SIHARAI_TYPE` | 個人向け支払方法を追加・定義する |
| 個人情報 | 現在なし | 誕生日など個人固有項目を追加する |

### 4.2 推奨テーブル方針

法人と個人では項目が異なり、現行は法人専用テーブルであるため、個人顧客用テーブルを新設する方針とする。

- `KOKYAKUKOJIN_TABLE`：個人顧客の氏名、住所、連絡先、メール、与信限度額、誕生日などを保持する。

- `KOKYAKUPASS_TABLE`：法人・個人共通の顧客コードとパスワードを保持する。

顧客共通情報を別テーブルへ正規化する案もあるが、現行プログラムの変更範囲が大きくなるため、ver.3では既存法人テーブルを維持し、個人テーブルを追加する方式を優先する。

### 4.3 個人顧客テーブル項目案

既存法人テーブルとの共通性を考慮し、以下を基本項目とする。

- `KOKYAKUCD CHAR(6) PRIMARY KEY`

- `KOKYAKUNAME VARCHAR(50) NOT NULL`

- `KOKYAKUKANA VARCHAR(50)`

- `ZIP CHAR(8)`

- `KENCD CHAR(2)`

- `ADDRESS1 VARCHAR(50)`、`ADDRESS2 VARCHAR(50)`

- `TEL CHAR(13)`、`FAX CHAR(13)`

- `MAIL VARCHAR(256)`

- `URIKAKE_ZAN INT`

- `YOSIN_GENDO INT`：個人は1,000,000

- `EIGYOUSHOCD CHAR(2)`

- `TOUROKU_D DATETIME`

- `BIRTHDAY DATEまたはDATETIME`

### 4.4 コード・採番方針

`CTR_CURCODE_TABLE`は現在、法人顧客用の`KOKYAKUHOUJIN_TABLE`を管理している。

個人顧客用には、次のいずれかを採用する。

1. `KOKYAKUKOJIN_TABLE`用の採番行を追加する。

2. 顧客種別ごとの採番管理テーブルを新設する。

現行構造との整合性を優先し、まずは`CTR_CURCODE_TABLE`に個人顧客用の採番行を追加する方式を推奨する。

個人顧客コードは、必ず先頭1桁が4～8になるように採番処理で保証する。

### 4.5 支払方法方針

`JUCHU_TABLE.SIHARAI_TYPE`の値定義を明文化する。

例：

| 値 | 支払方法 | 対象 |
|---|---|---|
| `0` | 月末一括払い | 法人 |
| `1` | 代金引換 | 個人 |
| `2` | 口座振込 | 個人 |

実装前に既存コードの値と重複しないことを確認する。

### 4.6 DBテスト

- 法人・個人の顧客情報がそれぞれ登録できること。

- 個人顧客コードが4～8で始まること。

- 個人顧客の与信限度額が1,000,000円で登録されること。

- 個人顧客の誕生日が保存・取得できること。

- 個人顧客の受注が`JUCHU_TABLE`に登録できること。

- 法人の既存受注データに影響がないこと。

## 5. ver.4 受注単位割引

### 5.1 DB改修対象

| 対象 | 現状 | 改修内容 |
|---|---|---|
| `JUCHU_TABLE` | `TOTALKINGAKU`のみで金額内訳がない | 小計、割引、税額、合計の内訳を保持 |
| `JUCHUMEISAI_TABLE` | 明細金額を保持 | 原則変更せず、受注単位で集計する |
| 顧客情報 | 顧客種別・誕生日を参照 | 割引判定に利用する |
| 受注登録処理 | 合計金額を登録 | 割引計算結果を登録する |

### 5.2 推奨カラム案

`JUCHU_TABLE`に次の項目を追加する方針を推奨する。

```sql
SUBTOTALKINGAKU INT(8) NOT NULL
,DISCOUNT_TYPE VARCHAR(20)
,DISCOUNT_RATE DECIMAL(5,2) DEFAULT 0
,DISCOUNTKINGAKU INT(8) DEFAULT 0
,TAXKINGAKU INT(8) NOT NULL
```

既存の`TOTALKINGAKU`は、割引・税を反映した最終合計金額として扱う。

### 5.3 計算・保存方針

計算順序は以下とする。

```text
明細金額合計 → 小計
小計・顧客種別・誕生日から割引判定
小計 - 割引額 → 課税対象額
課税対象額 × 消費税率 → 消費税額
課税対象額 + 消費税額 → 合計金額
```

割引条件は次の通り。

- 法人：小計が300,000円以上の場合、10%。

- 個人：受注日と誕生日の月日が一致する場合、50%。

### 5.4 税率の扱い

要件例では消費税5%が使用されているため、ver.4では税率を5%として扱う。

将来変更に備える場合は、税率をプログラム定数ではなく設定テーブルまたは管理項目として保持する。

### 5.5 DBテスト

- 法人の小計299,999円、300,000円、300,001円を確認する。

- 個人の誕生日一致・不一致を確認する。

- 割引額、税額、最終合計が保存値と画面表示で一致することを確認する。

- 割引なしの受注が正しく登録できることを確認する。

- 既存受注データの`TOTALKINGAKU`を破壊しないことを確認する。

## 6. ver.5 SQLインジェクション対策

### 6.1 DB改修対象

ver.5は基本的にDB構造変更ではなく、SQL発行方式の改修で対応する。

主な対象は以下である。

- `KOKYAKUPASS_TABLE`を検索するログイン認証SQL

- `KOKYAKUHOUJIN_TABLE`を検索する顧客処理

- 商品検索SQL

- 受注登録・在庫更新SQL

### 6.2 DB・認証情報の方針

- SQLの値を文字列連結せず、PreparedStatementのバインド変数を利用する。

- SQL文と入力値を分離する。

- パスワードの平文保存は現行仕様上の課題であるため、可能であればハッシュ化を別途検討する。

- ハッシュ化を実施する場合は、`KOKYAKUPASS_TABLE.PASSWORD CHAR(20)`では長さが不足する可能性があるため、`VARCHAR(255)`等への変更と既存データ移行が必要になる。

- ハッシュ化をver.5の必須範囲に含めない場合でも、平文保存が残ることを報告書に明記する。

### 6.3 DBテスト

- 正常な顧客コード・パスワードでログインできること。

- 誤った認証情報でログインできないこと。

- SQLインジェクション文字列を入力しても認証を突破できないこと。

- 特殊文字、空文字、長大文字列を入力してもSQLエラーにならないこと。

- PreparedStatement化後も既存の顧客・商品・受注処理が動作すること。

## 7. バージョンごとのDB改修まとめ

| Version | DB改修の中心 | 改修方式 |
|---|---|---|
| ver.2 | 商品カテゴリ、商品テーブル、サブカテゴリ、在庫、メーカー | 新規テーブル・初期データ追加 |
| ver.3 | 個人顧客、顧客採番、誕生日、支払方法 | 個人顧客テーブル新設、採番・受注項目拡張 |
| ver.4 | 受注金額内訳、割引、税額 | `JUCHU_TABLE`への金額項目追加 |
| ver.5 | 認証・各DAOのSQL発行方式 | 原則スキーマ変更なし。SQLのパラメータ化 |

## 8. SQLファイル管理方針

既存SQLを直接書き換えず、バージョンごとに改修SQLを分けて管理する。

```text
sql/
├─ create.sql
├─ insert.sql
├─ select.sql
├─ upgrade_ver2.sql
├─ upgrade_ver3.sql
├─ upgrade_ver4.sql
└─ upgrade_ver5.sql
```

各改修SQLには、次の内容をコメントで記載する。

- 対象バージョン

- 実行前提

- 実行順序

- 追加・変更するテーブルとカラム

- 初期データの内容

- ロールバック方法
