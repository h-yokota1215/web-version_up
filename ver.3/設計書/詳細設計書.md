## 2. 目的

本書は、受注管理システムのver.3において追加する個人顧客機能について、画面、処理、認証、顧客情報管理、受注処理およびデータベースアクセスの詳細を定義する。

ver.2までの法人顧客向け機能を基本的に維持しながら、個人顧客の登録、認証、受注を可能にする。

既存機能への影響を最小限に抑え、法人顧客と個人顧客の処理を適切に分離する。

## 3. 対象範囲

### 3.1 対象機能

- 個人顧客の新規登録
- 個人顧客の認証
- 個人顧客情報の登録・取得
- 個人顧客による受注
- 個人顧客の支払方法選択
- 個人顧客の与信判定
- 個人顧客の売掛残高更新
- 顧客コードの採番
- 既存法人顧客機能との共存

### 3.2 対象外

- ver.4で予定する割引機能
- ver.5で予定する認証機能の拡張
- ver.3の要件に含まれない既存機能の大規模な再設計
- 既存データベース構造の全面的な変更

## 4. 基本設計方針

### 4.1 既存機能の維持

法人顧客向けの登録、認証、受注および与信処理は、既存の動作を維持する。

個人顧客向けの処理を追加する際は、法人顧客向け処理への影響を確認し、必要な箇所に限定して修正する。

### 4.2 顧客種別ごとの処理分離

法人顧客と個人顧客では、登録項目、支払方法、与信判定などに違いがある。

そのため、顧客種別固有の処理は分離し、共通化できる処理のみ再利用する。

個人顧客の登録画面および登録処理は、既存の法人顧客用処理と分けて実装する。

### 4.3 データベース設計との整合性

個人顧客情報は新設する個人顧客テーブルに格納する。

認証情報については既存の認証情報テーブルを利用し、法人顧客と個人顧客の両方を扱う。

顧客情報と認証情報の整合性は、アプリケーション処理およびトランザクションによって保証する。新たな外部キー制約は追加しない。

## 5. 顧客種別と顧客コード

### 5.1 顧客種別の判定

顧客コードの先頭桁を使用して顧客種別を判定する。

| 顧客種別 | 顧客コードの先頭桁 |
|---|---|
| 法人顧客 | 1～3 |
| 個人顧客 | 4～8 |

認証時および顧客情報取得時には、顧客種別に応じた処理を選択する。

顧客コードの形式が不正な場合や、先頭桁から顧客種別を判定できない場合は、処理を継続せずエラーとして扱う。

### 5.2 個人顧客コード

個人顧客コードは6桁とする。

初期データとして、次の4件を登録する。

| 顧客コード | 用途 |
|---|---|
| 400000 | 個人顧客サンプル1 |
| 400001 | 個人顧客サンプル2 |
| 400002 | 個人顧客サンプル3 |
| 400003 | 個人顧客サンプル4 |

初期データ登録後の次回採番値は `400004` とする。

### 5.3 顧客コードの採番

顧客コードの採番には、既存の採番管理テーブル `CTR_CURCODE_TABLE` を使用する。

採番処理では、管理テーブルに保持された値を取得し、顧客コードを生成した後、次回採番値を更新する。

既存の採番処理の方式を基本的に踏襲する。

採番の同時実行制御については、現行方式の範囲で扱う。新たな排他制御方式の導入は、本設計では決定しない。

## 6. 個人顧客登録

### 6.1 処理概要

個人顧客の登録処理では、入力された個人顧客情報と認証情報を検証し、個人顧客テーブルおよび認証情報テーブルに登録する。

法人顧客の登録処理とは分離し、個人顧客固有の入力項目および登録条件を適用する。

### 6.2 入力項目

個人顧客の登録項目は、仕様書およびDB設計書に定義された項目に従う。

主な入力条件は次のとおりとする。

| 項目 | 入力条件 |
|---|---|
| 顧客コード | システムで採番する。顧客コードは6桁とし、先頭桁は4～8とする |
| 顧客名 | 必須。DB列は `VARCHAR(50) NOT NULL` |
| 顧客名カナ | DB列は `VARCHAR(50)`。NULLを許容する |
| 郵便番号 | 必須。DB列は `CHAR(8) NOT NULL` |
| 県コード | 必須。DB列は `CHAR(2) NOT NULL` |
| 住所1 | 必須。DB列は `VARCHAR(50) NOT NULL` |
| 住所2 | 必須。DB列は `VARCHAR(50) NOT NULL` |
| 連絡先電話番号 | 必須。DB列は `CHAR(13) NOT NULL` |
| FAX番号 | 任意。DB列は `CHAR(13)` で、NULLを許容する |
| メールアドレス | 新規登録時は必須。DB列は `VARCHAR(256)` で、NULLを許容する |
| 売掛残高 | DB列は `INT(8) NOT NULL`。初期値は0とする |
| 与信限度額 | DB列は `INT(8) NOT NULL`。個人顧客の与信限度額は1,000,000円とする |
| 営業所コード | 必須。DB列は `CHAR(2) NOT NULL` |
| 登録日 | 必須。DB列は `DATETIME NOT NULL` |
| 誕生日 | 必須。DB列は `DATE NOT NULL` |
| パスワード | 必須。既存の認証方式との整合性を確保する |

上表のDB列定義は、DB設計書に記載された内容に基づく。入力形式、桁数、日付の妥当性など、アプリケーション側で実施する具体的な入力チェックについては、実装内容と照合して確認する。

メールアドレスは新規登録時に必須とする一方、既存のサンプルデータにはNULLが含まれるため、データベース列自体はNULL許容とする。

FAX番号が未入力の場合は、空文字ではなくNULLを保存する。
既存サンプルデータのメールアドレスがNULLの場合は、その値を維持する。
新規登録時のメールアドレスは必須とし、未入力を許可しない。

また、顧客コードはシステムで採番し、利用者が任意の値を入力する方式とはしない。

### 6.3 入力チェック

登録処理では、少なくとも次の検証を行う。

1. 必須項目が入力されていること。
2. 各項目が定義された形式および桁数を満たしていること。
3. 誕生日が有効な日付であること。
4. 顧客コードがシステムによって適切に採番されていること。
5. 認証情報の登録に必要な項目が満たされていること。

メールアドレスは新規登録時に必須とする。ただし、既存のサンプルデータに含まれるメールアドレスの `NULL` は許容する。

したがって、メールアドレスの必須条件はアプリケーションの新規登録処理で検証し、データベース列自体はNULL許容とする。

### 6.4 メールアドレスの重複

メールアドレスの重複チェックは、顧客種別によって扱いを分ける。

- 法人顧客同士のメールアドレス重複チェックは、既存仕様を維持する。
- 個人顧客登録では、既存の個人顧客とメールアドレスが重複していても登録を許可する。
- 法人顧客と個人顧客の間でメールアドレスが重複していても登録を許可する。

個人顧客の識別には、顧客コードおよびパスワードを使用する。

既存の法人顧客用メール重複チェック処理を個人顧客登録にそのまま適用しないこと。

### 6.5 誕生日

誕生日は必須項目とする。

データベース上の型は `DATE` とし、NULLを許可しない。

画面入力値を日付として検証し、適切な形式に変換して登録する。

### 6.6 登録処理の順序

登録処理は、次の順序を基本とする。

1. 入力値を受け取る。
2. 必須項目および書式を検証する。
3. 個人顧客用の重複チェックなど、必要な検証を行う。
4. トランザクションを開始する。
5. 顧客コードを採番する。
6. 個人顧客情報を個人顧客テーブルに登録する。
7. 認証情報を認証情報テーブルに登録する。
8. 正常終了時にコミットする。
9. エラー発生時にロールバックし、エラーを通知する。

具体的なDAOメソッド名、SQLおよびトランザクション制御の実装詳細は、実際のソースコードと照合して確定する。

### 6.7 登録時の整合性

個人顧客情報と認証情報のいずれか一方のみが登録される状態を防止する。

登録処理中にエラーが発生した場合は、トランザクションをロールバックし、登録内容の不整合を防ぐ。

新たな外部キー制約は追加せず、アプリケーション処理およびトランザクションで整合性を保証する。

## 7. 認証処理

### 7.1 処理概要

認証処理では、入力された顧客コードおよびパスワードを使用して認証情報を確認する。

顧客コードの先頭桁から顧客種別を判定し、法人顧客または個人顧客に対応した処理を実行する。

### 7.2 認証処理の流れ

1. 顧客コードおよびパスワードを受け取る。
2. 必須入力および顧客コード形式を検証する。
3. 顧客コードの先頭桁から顧客種別を判定する。
4. 認証情報テーブルから対象の認証情報を取得する。
5. パスワードを照合する。
6. 認証に成功した場合、顧客種別に対応する顧客情報を取得する。
7. 認証結果を画面に返す。

### 7.3 顧客種別別の処理

| 顧客種別 | 顧客情報の取得先 |
|---|---|
| 法人顧客 | 既存の法人顧客テーブル |
| 個人顧客 | 新設する個人顧客テーブル |

法人顧客の認証処理は既存の動作を維持する。

個人顧客の認証では、法人顧客専用のDAOやデータクラスへの固定的な依存を避け、個人顧客用の取得処理を利用する。

### 7.4 認証失敗

次の場合は認証失敗として扱う。

- 顧客コードが未入力である。
- パスワードが未入力である。
- 顧客コードの形式が不正である。
- 顧客コードに対応する認証情報が存在しない。
- パスワードが一致しない。
- 顧客情報を正常に取得できない。

エラーメッセージの具体的な文言は、既存画面の仕様およびセキュリティ要件との整合性を確認して決定する。

## 8. 個人顧客情報の取得

### 8.1 取得方針

顧客種別に応じて、対応する顧客テーブルから情報を取得する。

法人顧客の情報取得処理は既存処理を維持し、個人顧客については個人顧客テーブルを参照する。

### 8.2 DAOの責務

DAOは、データベースへのアクセス、SQLの実行および取得結果のデータ変換を担当する。

顧客種別固有のSQLやテーブル構造を、法人顧客用DAOに無理に集約しない。

共通化する場合は、既存のクラス構造およびデータモデルとの整合性を確認する。

## 9. 受注処理

### 9.1 基本方針

個人顧客による受注を追加する。

既存の受注テーブル `JUCHU_TABLE` および受注明細テーブル `JUCHUMEISAI_TABLE` を基本的に再利用し、既存の法人顧客向け受注機能への影響を最小限に抑える。

### 9.2 顧客情報の取得

受注処理では、認証済み顧客の顧客コードを使用して顧客情報を取得する。

顧客種別に応じて、法人顧客または個人顧客の情報を参照する。

顧客情報の取得に失敗した場合は、受注処理を継続しない。

### 9.3 受注データの登録

受注処理では、既存の受注・受注明細の登録方式を基本的に踏襲する。

登録対象には、受注情報、受注明細情報および必要な顧客関連情報を含める。

複数テーブルへの登録が必要な場合は、関連する登録処理の整合性を確保する。

具体的なSQL、DAOメソッドおよび登録順序は、既存実装との照合後に確定する。

## 10. 支払方法

### 10.1 支払方法コード

支払方法コードは、次の定義に統一する。

| 支払コード | 支払方法 | 対象顧客 |
|---|---|---|
| `0` | 月末一括払い | 法人顧客 |
| `1` | 代金引換 | 個人顧客 |
| `2` | 銀行振込 | 個人顧客 |

既存の法人顧客における月末一括払いのコード `0` を維持する。

### 10.2 顧客種別ごとの選択条件

法人顧客は、既存の月末一括払いを使用する。

個人顧客は、代金引換または銀行振込を選択できる。

顧客種別に対応しない支払方法が指定された場合は、不正な組み合わせとして扱う。

### 10.3 支払方法の保存

受注データには、選択された支払方法コードを保存する。

支払方法コードの変換および表示処理は、本節の定義と整合させる。

既存の `Juchu` クラスにおける支払方法設定処理について、月末一括払いを固定設定する既存メソッドを個人顧客向け処理にそのまま適用しない。

個人顧客の支払方法を正しく設定・取得できるようにし、既存の法人顧客向け動作を維持する。

## 11. 与信判定および売掛残高更新

### 11.1 基本方針

与信判定および売掛残高更新は、顧客種別と支払方法の組み合わせによって処理を分ける。

### 11.2 処理条件

| 顧客種別 | 支払方法 | 与信判定 | 売掛残高更新 |
|---|---|---|---|
| 法人顧客 | 月末一括払い | 実施する。既存処理を維持する | 実施する。既存処理を維持する |
| 個人顧客 | 代金引換 | 実施しない | 実施しない |
| 個人顧客 | 銀行振込 | 実施する | 実施する |

### 11.3 個人顧客の与信限度額

個人顧客の与信限度額は100万円とする。

個人顧客が銀行振込を選択した場合、既存の与信判定の考え方を基本として、個人顧客の売掛残高および今回の受注額を考慮し、与信限度額を超過しないことを確認する。

与信判定に必要な顧客情報は、個人顧客テーブルから取得する。

### 11.4 代金引換の処理

個人顧客が代金引換を選択した場合は、与信判定および売掛残高更新を行わない。

代金引換の受注に対して、法人顧客用の与信判定や売掛残高更新を誤って実行しないこと。

### 11.5 法人顧客の処理

法人顧客については、既存の与信判定および売掛残高更新を維持する。

個人顧客向け処理の追加によって、法人顧客の与信判定条件や残高更新先が変わらないようにする。

### 11.6 実装上の注意

既存の `DaoJuchu` では、与信判定および売掛残高更新が法人顧客テーブルを前提としている。

個人顧客の銀行振込に対応するため、顧客種別に応じた与信情報の取得先および残高更新先を選択できるようにする。

既存の法人顧客向けSQLおよび処理結果を維持しながら、個人顧客用の処理を追加する。

## 12. データベースアクセス

### 12.1 利用するテーブル

| テーブル | 用途 |
|---|---|
| `KOKYAKUHOUJIN_TABLE` | 法人顧客情報 |
| `KOKYAKUKOJIN_TABLE` | 個人顧客情報 |
| `KOKYAKUPASS_TABLE` | 認証情報 |
| `JUCHU_TABLE` | 受注情報 |
| `JUCHUMEISAI_TABLE` | 受注明細情報 |
| `CTR_CURCODE_TABLE` | 採番管理 |

実際のテーブル定義および列名はDB設計書を正とする。

### 12.2 トランザクション

個人顧客登録では、個人顧客情報と認証情報の登録を整合性のある単位として扱う。

受注処理についても、既存の登録処理におけるトランザクション構成を確認し、関連するデータの不整合を防止する。

トランザクション境界やコミット・ロールバックの具体的な実装は、既存ソースコードとの照合を行ったうえで確定する。

### 12.3 外部キー制約

ver.3では、新たな外部キー制約を追加しない。

顧客情報と認証情報の整合性は、アプリケーション処理およびトランザクションによって保証する。

## 13. エラー処理

### 13.1 基本方針

入力エラー、認証失敗、顧客情報取得失敗、データベース処理失敗などを検知した場合は、異常な状態のまま処理を継続しない。

エラー発生時には、既存システムの例外処理および画面遷移の方針に従って処理する。

### 13.2 主なエラー条件

- 必須入力項目の未入力
- 入力形式または桁数の不正
- 顧客コードの形式不正
- 認証失敗
- 顧客情報の取得失敗
- 顧客種別と支払方法の不整合
- 与信限度額超過
- 顧客情報の登録失敗
- 認証情報の登録失敗
- 受注情報または受注明細情報の登録失敗
- 採番処理の失敗

### 13.3 ロールバック

トランザクション内でエラーが発生した場合は、ロールバックを実施し、関連データが不整合な状態で残らないようにする。

具体的な例外の種類、ログ出力、画面表示文言は、既存実装との照合後に確定する。

## 17. 設計上の決定事項

本書では、以下を決定事項として扱う。

- 個人顧客登録処理は法人顧客登録処理から分離する。
- 個人顧客の誕生日は必須とし、DB型は `DATE`、NULL不可とする。
- メールアドレスは新規登録時に必須とするが、DB列はNULL許容とする。
- 法人顧客同士のメール重複チェックは維持する。
- 個人顧客同士および法人・個人間のメール重複は許容する。
- 支払方法コードは `0=月末一括払い`、`1=代金引換`、`2=銀行振込` とする。
- 個人顧客の代金引換では与信判定・売掛残高更新を行わない。
- 個人顧客の銀行振込では与信判定・売掛残高更新を行い、与信限度額は100万円とする。
- 個人顧客の初期サンプルコードは `400000`～`400003` とし、次回採番値は `400004` とする。
- 新たな外部キー制約は追加しない。
- 採番の同時実行制御は既存方式の範囲で扱う。
- 未回答・未確認事項は未決定のまま管理する。
