## 2. 改修の背景と目的

本改修では、既存の法人顧客を対象とした受注管理システムを拡張し、個人顧客に対しても顧客登録および受注を行えるようにする。

個人顧客の受注処理は、基本的に既存の法人顧客向け受注処理を再利用する。ただし、顧客情報の管理、与信限度額、売掛残高、支払方法など、法人顧客と個人顧客で異なる条件を考慮する必要がある。

本改修の目的は、次のとおりとする。

- 個人顧客を登録・管理できるようにする。
- 個人顧客が商品を注文できるようにする。
- 法人顧客と個人顧客の支払条件の違いを扱えるようにする。
- 既存の受注処理を可能な限り再利用し、既存機能への影響を抑える。
- 提供されたサンプルデータを利用して、個人顧客の登録・受注機能を検証できるようにする。

## 4. 現状の整理

### 4.1 既存システム

ver.2では、法人顧客を中心とした顧客管理および受注処理が実装されている。

既存実装の調査対象は次のとおりである。

| 対象 | 主な確認内容 |
|---|---|
| `KokyakuControl.java` | 顧客情報の取得・登録などの制御 |
| `DaoControl.java` | 顧客種別に応じたDAOの振り分け |
| `DaoJuchu.java` | 受注処理および売掛残高更新処理 |
| `cosd1060.jsp` | 支払方法の選択画面 |
| `KOKYAKUHOUJIN_TABLE` | 法人顧客情報の管理 |
| `KOKYAKUPASS_TABLE` | 顧客認証情報の管理 |
| `CTR_CURCODE_TABLE` | コード管理に関係する既存処理 |
| `JUCHU_TABLE` | 受注情報および支払区分の管理 |
| `JUCHUMEISAI_TABLE` | 受注明細の管理 |

### 4.2 現状の課題

1. 顧客管理処理が法人顧客を前提としている箇所がある。
2. 個人顧客を登録・管理するためのデータ構造および処理を追加する必要がある。
3. 顧客種別に応じた登録・検索・認証処理の対応が必要である。
4. 支払方法の選択画面は、現状では「月末一括お支払い」を中心とした構成である。
5. 個人顧客の受注時には、法人顧客とは異なる支払条件および与信条件を考慮する必要がある。
6. 既存の受注処理を再利用する範囲と、個人顧客向けに分岐させる範囲を明確にする必要がある。
7. 顧客登録・認証処理のDAO呼び出し先が法人顧客を前提としているため、個人顧客に対応する処理を追加する必要がある。
8. 受注時の売掛残高更新先が法人顧客テーブルに固定されているため、個人顧客の受注に対応するには更新処理の見直しが必要である。

## 8. データベース改修の検討

### 8.1 個人顧客テーブル

既存の法人顧客テーブル `KOKYAKUHOUJIN_TABLE` とは別に、個人顧客を管理する `KOKYAKUKOJIN_TABLE` を新設する案を検討する。

これは全体改修方針を踏まえた設計候補であり、最終的なテーブル名・列定義・制約は設計書で確定する。

### 8.2 関連テーブル

| テーブル | 改修上の確認事項 |
|---|---|
| `KOKYAKUHOUJIN_TABLE` | 法人顧客の既存データ・処理を維持できるか |
| `KOKYAKUKOJIN_TABLE` | 個人顧客情報の保存先として新設するか |
| `KOKYAKUPASS_TABLE` | 法人・個人で認証情報を共有する構造が適切か |
| `CTR_CURCODE_TABLE` | 個人顧客コードを既存のコード管理方式で採番できるか |
| `JUCHU_TABLE` | 支払区分を保存する既存項目を利用できるか |
| `JUCHUMEISAI_TABLE` | 個人顧客の受注明細を既存構造で扱えるか |

### 8.3 売掛残高の扱い

既存の受注処理では、`DaoJuchu.insertData()` において、顧客の与信限度額と売掛残高を参照し、今回の受注金額を加算した金額を基に与信判定を行っている。また、売掛残高の更新先は、現状では `KOKYAKUHOUJIN_TABLE` に固定されている。

個人顧客への対応にあたっては、個人顧客の支払方法が代金引換または銀行振込であることを踏まえ、与信判定および売掛残高の管理方法を検討する必要がある。

ただし、個人顧客の受注時に売掛残高を更新するか、支払方法によって処理を変更するかについては、現時点では確定しない。

本事項は未確定事項として管理し、詳細設計までに業務上の扱いを整理したうえで、仕様およびデータ更新処理を確定する。

検討事項：

- 法人顧客と個人顧客の識別方法
- 顧客コードによる検索先の振り分け
- パスワード情報を共有する場合の識別方法
- 既存法人顧客のログイン動作への影響

### 9.3 個人顧客の受注

個人顧客の受注処理は、基本的に法人顧客向けの既存処理を再利用する。

検討事項：

- ログイン中の顧客情報の取得方法
- 受注データと顧客情報の関連付け
- 支払方法の選択と保存
- 与信限度額の適用方法
- 売掛残高の更新要否および更新タイミング
- 受注明細の既存構造を再利用できるか

### 9.4 支払方法

| 顧客種別 | 支払方法 |
|---|---|
| 法人顧客 | 月末一括払い |

## 13. 初版のまとめ

ver.3では、個人顧客の登録・管理と受注を追加し、法人顧客とは異なる支払条件を扱えるようにすることが主な改修要求である。

実装にあたっては、既存の法人顧客向け処理を可能な限り再利用しながら、個人顧客情報の管理、認証、顧客コード、与信限度額、支払方法および売掛残高の扱いを整理する必要がある。

## 14. 既存コード・DB定義との照合結果

本章では、ver.2の既存ソースコードおよびDB定義を調査して確認できた事実を整理する。既存実装の説明と、ver.3で決定する仕様は区別する。

### 14.1 顧客登録・認証処理

既存の顧客登録処理では、DAOの呼び出し先が法人顧客用の `DaoHoujin` となっている。また、顧客情報の取得処理も法人顧客テーブルを参照する構造となっている。

個人顧客への対応には、個人顧客用の登録・検索処理と、顧客種別に応じたDAOの振り分けを検討する必要がある。

### 14.2 顧客コードの採番

既存の法人顧客登録処理では、`CTR_CURCODE_TABLE` の法人顧客用採番情報を利用して顧客コードを取得・更新している。

個人顧客コードには先頭1桁が4～8という条件があるため、法人顧客用の採番処理をそのまま利用できるとは限らない。個人顧客用の採番方式および初期値は、別途決定する。

### 14.3 支払方法

既存の支払方法選択画面では、値 `0` の「月末一括お支払い」が設定されている。選択された値は受注データに引き渡され、`JUCHU_TABLE.SIHARAI_TYPE` に保存される構造である。

個人顧客向けの代金引換および銀行振込については、既存値との整合性を確認し、支払方法コードと画面表示を仕様化する。

### 14.4 与信判定・売掛残高更新

既存の受注処理では、与信限度額と売掛残高を基に与信判定を行う。また、売掛残高の更新先は `KOKYAKUHOUJIN_TABLE` に固定されている。

個人顧客の受注にこの処理を適用する場合、個人顧客の支払条件に応じた与信判定および売掛残高の管理方法を検討する必要がある。

個人顧客の売掛残高の扱いは、現時点では未確定とし、詳細設計までに業務ルールを確定する。

### 14.5 調査結果の取り扱い

本章で確認した内容は、ver.2の既存実装に関する調査結果である。ver.3の最終的な処理方式、DB構造、コード値などは、改修要件と照合したうえで仕様書・設計書に反映する。


次工程では、既存コード・DB定義・改修要件資料との照合結果を踏まえて仕様を具体化する。特に、個人顧客コードの採番方法、支払方法コードの対応関係、個人顧客の売掛残高の扱いは、詳細設計までに確定する。
